Zig frente a C: notas para programación de sistemas

C sigue siendo el lenguaje que más leo. Para código nuevo prefiero Zig: mantiene el mismo nivel de control y detecta más errores en compilación o en modo debug. Estas son las diferencias que más pesan en la práctica.

1. Liberar recursos: goto vs defer/errdefer

En C, la limpieza en orden inverso suele resolverse con una cadena de etiquetas:

int load(const char *path, char **out) {
    int rc = -1;
    FILE *f = fopen(path, "rb");
    if (!f) goto done;

    char *buf = malloc(4096);
    if (!buf) goto close_file;

    if (fread(buf, 1, 4096, f) == 0) goto free_buf;

    *out = buf;
    rc = 0;
    goto close_file;

free_buf:
    free(buf);
close_file:
    fclose(f);
done:
    return rc;
}

En Zig, cada recurso declara su limpieza junto a su adquisición:

fn load(gpa: std.mem.Allocator, path: []const u8) ![]u8 {
    const file = try std.fs.cwd().openFile(path, .{});
    defer file.close(); // siempre

    const buf = try gpa.alloc(u8, 4096);
    errdefer gpa.free(buf); // solo si se retorna un error

    const n = try file.read(buf);
    if (n == 0) return error.EmptyFile;
    return try gpa.realloc(buf, n);
}

defer se ejecuta al salir del bloque y errdefer, solo en la salida por error. Agregar un recurso nuevo no obliga a reordenar etiquetas.

Las rutas de fallo también se pueden probar. checkAllAllocationFailures repite la función y hace fallar cada asignación, una por una. std.testing.allocator reporta las fugas de memoria:

test "load no pierde memoria" {
    try std.testing.checkAllAllocationFailures(std.testing.allocator, loadForTest, .{});
}

2. La longitud viaja con el dato

int sum(const int *xs, size_t n) {
    int s = 0;
    for (size_t i = 0; i <= n; i++)   /* lee xs[n]: fuera de rango */
        s += xs[i];
    return s;
}

C compila esto sin advertencias y lee memoria ajena en silencio. En Zig, un slice ([]T) es puntero + longitud:

fn sum(xs: []const i32) i32 {
    var s: i32 = 0;
    for (xs) |x| s += x;
    return s;
}

Con el mismo error de índice, el resultado es un panic inmediato en Debug y ReleaseSafe:

var i: usize = 0;
while (i <= xs.len) : (i += 1) s += xs[i];
// panic: index out of bounds: index 3, len 3

Los strings son []const u8: no hace falta strlen() ni existe el terminador \0 olvidado.

3. Errores que no se pueden ignorar

FILE *f = fopen("config.ini", "r");
fgets(line, sizeof line, f);   /* si f es NULL: comportamiento indefinido */

En Zig, el error forma parte del tipo de retorno (!T). El compilador obliga a manejarlo:

const file = std.fs.cwd().openFile("config.ini", .{}) catch |err| switch (err) {
    error.FileNotFound => return defaultConfig(),
    else => return err,
};
defer file.close();

Si se omite el resultado, el programa no compila:

std.fs.cwd().deleteFile("tmp.txt");
// error: error union is ignored

Las opciones son try (propagar), catch (manejar) o if (x) |v| ... else |err| ....

4. comptime en lugar del preprocesador

Las macros de C sustituyen texto:

#define MAX(a, b) ((a) > (b) ? (a) : (b))
int m = MAX(i++, j);   /* i++ puede evaluarse dos veces */

#ifdef _WIN32
#define SEP '\\'
#else
#define SEP '/'
#endif

En Zig se escribe código normal que se evalúa en compilación:

const builtin = @import("builtin");

fn max(comptime T: type, a: T, b: T) T {
    return if (a > b) a else b;
}

const sep: u8 = if (builtin.os.tag == .windows) '\\' else '/';

Para los genéricos se usa una función que retorna un tipo:

fn Stack(comptime T: type, comptime cap: usize) type {
    return struct {
        items: [cap]T = undefined,
        len: usize = 0,

        pub fn push(self: *@This(), x: T) error{Full}!void {
            if (self.len == cap) return error.Full;
            self.items[self.len] = x;
            self.len += 1;
        }
    };
}

var s: Stack(u32, 16) = .{};
try s.push(42);

Los argumentos se evalúan una sola vez, hay comprobación de tipos y los errores de compilación son legibles.

5. Overflow con semántica explícita

int x = INT_MAX;
x = x + 1;   /* overflow con signo: comportamiento indefinido */

En Zig, la intención se escribe en el operador:

const x: i32 = std.math.maxInt(i32);

const w = x +% 1;                 // wrapping:   -2147483648
const s = x +| 1;                 // saturación:  2147483647
const r = @addWithOverflow(x, 1); // .{ -2147483648, 1 }

var y = x;
y += 1; // Debug/ReleaseSafe: panic: integer overflow

6. Zig también compila C

zig cc es un compilador de C (Clang) con soporte de compilación cruzada integrado:

zig cc -O2 -o hello hello.c
zig cc -target x86_64-linux-musl -static -o hello hello.c
zig cc -target aarch64-macos -o hello hello.c

C y Zig pueden convivir en el mismo build.zig:

exe.root_module.addCSourceFile(.{
    .file = b.path("src/legacy.c"),
    .flags = &.{"-std=c11"},
});
exe.root_module.link_libc = true;

Esto permite migrar un proyecto archivo por archivo.

7. Límites

  • Zig no evita use-after-free ni punteros a variables locales que ya no existen.
  • En ReleaseFast y ReleaseSmall se eliminan casi todas las comprobaciones de seguridad.
  • El lenguaje aún no llega a 1.0, así que sus APIs cambian entre versiones.
  • C tiene un ABI estable, más ecosistema y soporte para más arquitecturas.

Para leer código existente, C sigue siendo indispensable. Para escribir código nuevo, Zig ofrece el mismo control y más errores detectados antes de producción.
