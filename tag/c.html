Lista doblemente enlazada en el kernel Linux

El kernel Linux es una pieza de código enorme. Como todo kernel de un sistema operativo moderno, contiene planificadores que administran procesos y recursos, una pila de red, varios sistemas de archivos, miles de controladores de dispositivos y muchísimo más. Al mismo tiempo, tiene que gestionar todo esto de la forma más eficiente posible. Y la eficiencia no siempre consiste en escribir instrucciones más rápidas o algoritmos ingeniosos. Muy a menudo, como en cualquier aplicación de espacio de usuario, empieza con una pregunta mucho más fundamental: ¿cómo están organizados los datos?

Como escribió alguna vez Linus Torvalds:

Los buenos programadores se preocupan por las estructuras de datos y sus relaciones.

— Linus Torvalds, lista de correo de git, 27 de julio de 2006

El kernel necesita llevar la cuenta de procesos, páginas de memoria, archivos, temporizadores, dispositivos, conexiones de red e innumerables objetos más. Algunos deben buscarse rápido, otros deben mantenerse siempre ordenados, otros se recorren con frecuencia y otros tienen que insertarse o eliminarse con el menor costo posible. Elegir una representación adecuada para estos datos puede influir directamente en el rendimiento y en el consumo de memoria.

Esto es especialmente importante en un software como el kernel de un sistema operativo. Idealmente, debería ser casi invisible para el usuario y añadir la menor sobrecarga posible.

Si alguna vez has leído el código fuente del kernel, probablemente notaste que listas enlazadas, árboles, colas, mapas de bits, tablas hash y muchas otras estructuras de datos aparecen en casi todos sus subsistemas. Algunas resultan familiares por los libros clásicos de ciencias de la computación; otras se adaptaron a los requisitos particulares y al estilo de programación del kernel.

En este artículo veremos uno de estos bloques básicos, para reconocerlo cuando exploremos los principales subsistemas del kernel.

Listas enlazadas

La primera estructura de datos que veremos es la lista enlazada.

Me parece una buena elección para empezar porque, por un lado, es relativamente sencilla y, por otro, es omnipresente. Decir que es omnipresente no es exagerar: encontramos listas enlazadas en muchas partes distintas del kernel. Para tener una idea aproximada de cuán común es:

rg -w 'struct list_head' | wc -l
17143

¡Más de diecisiete mil apariciones! Sin duda vale la pena entender cómo se implementa y se usa la lista enlazada en el kernel.

Uno de los usos principales de esta estructura es organizar distintos tipos de objetos en secuencias. Pero antes de entrar en la implementación del kernel, repasemos brevemente la estructura en general.

Según Wikipedia:

En ciencias de la computación, una lista enlazada es una estructura de datos lineal compuesta por una secuencia de nodos. Cada nodo almacena uno o más valores de datos y una o varias referencias —también llamadas enlaces o punteros— hacia otros nodos de la lista.

— Wikipedia, «Lista enlazada»

En otras palabras, a diferencia de un arreglo, los elementos de una lista enlazada no tienen que ocupar posiciones contiguas en memoria. La relación entre ellos se representa explícitamente mediante enlaces. En el caso más simple, cada nodo contiene un único enlace al nodo siguiente:

Una lista así se llama lista simplemente enlazada y solo puede recorrerse en un sentido: partimos de head y seguimos el puntero next de cada nodo hasta llegar al final. Su definición y la implementación de sus operaciones básicas son bastante simples. Si has leído, por ejemplo, Algorithms de Robert Sedgewick y Kevin Wayne, conoces la representación clásica:

private class Node
{
    Item item;
    Node next;
}

Cada Node guarda un elemento y una referencia al nodo siguiente. Por ejemplo, si la lista contiene tres elementos, el primer nodo apunta al segundo y el segundo al tercero. El último nodo no apunta a nada: su enlace vale null, y así se determina el final de la lista.

Agregar un elemento nuevo no exige mover los elementos existentes en memoria: basta con crear un nodo y ajustar los enlaces correspondientes. Para eliminar un elemento, cambiamos el enlace del nodo anterior para que se salte el nodo eliminado.

Muchas veces esto no es suficiente. Algunas operaciones necesitan recorrer la lista hacia atrás. En esos casos, cada nodo recibe un segundo enlace que apunta al nodo anterior. Esta estructura se llama lista doblemente enlazada y, esquemáticamente, se ve así:

Listas enlazadas en el kernel Linux

Una vez repasada la idea básica, veamos cómo las implementa el kernel Linux.

Antes de ver esa implementación, esperaba algo muy parecido a lo anterior: una estructura simple con un puntero o espacio para los datos y una referencia a otro nodo. ¡Resultó ser bastante distinta!

El kernel implementa las llamadas listas enlazadas intrusivas. En ellas no hay un puntero a los datos. El nodo de la lista contiene solo dos punteros: uno al elemento siguiente y otro al anterior. Ese nodo se incrusta dentro de la estructura que queremos guardar en la lista, y los enlaces conectan estos nodos incrustados:

Sí, al principio puede parecer muy raro. ¿Cómo puede una estructura así representar una lista de procesos, dispositivos, archivos o cualquier otro objeto del kernel si no contiene los objetos? La respuesta es justamente una de las ideas características de la implementación de Linux: en lugar de guardar el objeto dentro del nodo de la lista, se guarda el nodo de la lista dentro del objeto.

La implementación de las listas enlazadas del kernel está en include/linux/list.h. La estructura en sí refleja la idea que acabamos de describir:

struct list_head {
    struct list_head *next, *prev;
};

La estructura list_head contiene solo dos punteros: al nodo siguiente y al anterior. ¿Cómo se usa, entonces? Se incrusta un list_head directamente en la estructura cuyos objetos queremos mantener en una lista. Por ejemplo, la estructura que define un proceso tiene, entre otros campos:

struct task_struct {
    ...
    struct list_head tasks;
    ...
};

El campo tasks sirve para enlazar objetos task_struct entre sí. Así, en lugar de reservar un nodo de lista aparte que contenga un puntero a un task_struct, cada task_struct contiene su propio nodo. Lo interesante es que los punteros next y prev no apuntan directamente a otro task_struct, sino al miembro tasks incrustado en los task_struct vecinos. Esquemáticamente:

Este enfoque nos da una lista enlazada sin reservar memoria aparte para cada nodo y sin que list_head tenga que saber nada de las estructuras que enlaza.

Suena muy bien, pero la primera vez que uno lo ve surge otra pregunta: si al recorrer la lista solo tenemos un puntero a list_head, ¿cómo volvemos al task_struct que lo contiene? La respuesta se apoya en otro auxiliar muy común del kernel: la macro container_of. Esta macro nos da un puntero a la estructura que nos interesa; en nuestro caso, a partir de un puntero al miembro tasks obtenemos el task_struct que lo contiene.

La idea es bastante simple. Si conocemos la dirección de un nodo de lista incrustado en una estructura, el tipo de la estructura y el nombre del campo que representa el nodo, podemos calcular la dirección de la propia estructura. Aquí tenemos un puntero al miembro tasks, que es un list_head, y sabemos que ese miembro pertenece a la estructura task_struct. Con esa información, el kernel obtiene la dirección del task_struct.

Esto es exactamente lo que permite que la implementación de las listas siga siendo genérica: list_head no sabe nada de task_struct, y aun así el código que usa la lista siempre puede volver al objeto que contiene el nodo.

Entendida la idea básica, veamos la implementación de container_of. La definición de la macro está en include/linux/container_of.h:

/**
 * container_of - cast a member of a structure out to the containing structure
 * @ptr:    the pointer to the member.
 * @type:   the type of the container struct this is embedded in.
 * @member: the name of the member within the struct.
 *
 * WARNING: any const qualifier of @ptr is lost.
 * Do not use container_of() in new code.
 */
#define container_of(ptr, type, member) ({              \
    static_assert(__same_type(*(ptr), typeof_member(type, member)) || \
              __same_type(*(ptr), void),            \
              "pointer type mismatch in container_of()");   \
    (type *)((void *)(ptr) - offsetof(type, member)); })

La macro recibe tres argumentos:

  • el puntero al nodo de la lista;
  • el tipo de la estructura que contiene el nodo;
  • el nombre del campo que representa el nodo.

En el ejemplo anterior, estos argumentos corresponderían a:

  • el puntero al campo tasks;
  • struct task_struct, como tipo que contiene el nodo;
  • tasks, como nombre del campo que representa el nodo.

La primera línea del cuerpo de la macro no tiene que ver con el cálculo de la dirección: solo hace una comprobación de tipos en tiempo de compilación para asegurar que el puntero al nodo tenga el tipo esperado.

La segunda línea hace el trabajo real. Con la macro offsetof calcula el desplazamiento desde el inicio de la estructura hasta el campo que define el nodo. Conocido ese desplazamiento, lo restamos de la dirección del nodo y obtenemos la dirección de la estructura que lo contiene.

¡Y eso es básicamente todo! En abstracto, container_of nos da la dirección de una estructura cuando conocemos la dirección de uno de sus campos. Llevado al contexto de las listas enlazadas, no es más que obtener la entrada real de la lista a partir de un puntero a su nodo incrustado:

/**
 * list_entry - get the struct for this entry
 * @ptr:    the &struct list_head pointer.
 * @type:   the type of the struct this is embedded in.
 * @member: the name of the list_head within the struct.
 */
#define list_entry(ptr, type, member) \
    container_of(ptr, type, member)

Operaciones sobre listas

En la sección anterior conocimos la estructura básica de las listas enlazadas del kernel. Ahora veamos las operaciones para agregar, eliminar y actualizar elementos.

Simplemente enumerar la API existente sería bastante aburrido. Es mucho más interesante ver un ejemplo real de uso: algún mecanismo que probablemente hayas visto al usar Linux, pero sin pensar en lo que ocurre por detrás.

El kernel usa listas en muchísimos lugares. Tomemos, por ejemplo, los dispositivos de caracteres misceláneos (misc).

Cada dispositivo de caracteres se identifica con un par de números: el número mayor (major) y el menor (minor). El mayor suele identificar al controlador o a un grupo de dispositivos relacionados, y el menor, a un dispositivo concreto que maneja ese controlador.

El kernel ofrece una API especial que permite a un controlador registrar un dispositivo de caracteres sin asignarle un número mayor propio. Todos esos dispositivos comparten el mismo número mayor y cada uno recibe su propio número menor. Ese número mayor es:

#define MISC_MAJOR      10

Desde el espacio de usuario, los dispositivos misceláneos se ven como dispositivos de caracteres normales con el mismo número mayor y distintos números menores. Lo que nos interesa es cómo el kernel lleva internamente la cuenta de todos ellos.

Cada dispositivo misceláneo se representa con una estructura miscdevice, definida en include/linux/miscdevice.h. Entre otros, esta estructura tiene un campo llamado list, que permite al dispositivo formar parte de la lista enlazada que mantiene el subsistema misc:

struct miscdevice {
    int minor;
    const char *name;
    const struct file_operations *fops;
    struct list_head list;
    struct device *parent;
    struct device *this_device;
    const struct attribute_group **groups;
    const char *nodename;
    umode_t mode;
};

Ya sabemos cómo usará el kernel el campo list: cada dispositivo registrado contiene su propio nodo, y todos están enlazados en una única lista con la que el kernel les sigue la pista. Hasta aquí debería quedar claro cómo se manejan y enlazan los nodos. Pero ¿cómo accedemos a la lista en sí? Necesitamos una referencia a su cabeza:

static LIST_HEAD(misc_list);

Siguiendo las definiciones de las macros LIST_HEAD y LIST_HEAD_INIT en include/linux/list.h, esto se expande a una inicialización de estructura C corriente:

struct list_head misc_list = { &(misc_list), &(misc_list) }

Los dos valores del inicializador son los campos next y prev de la estructura list_head. Como al principio la lista está vacía, no hay otros nodos a los que apuntar, así que ambos apuntan a la propia cabeza.

Cuando el kernel registra un dispositivo, inicializa la estructura miscdevice correspondiente y la agrega a la lista con:

list_add(&misc->list, &misc_list);

Esta función está definida en include/linux/list.h y luce así:

static __always_inline void list_add(struct list_head *new,
                     struct list_head *head)
{
    __list_add(new, head, head->next);
}

Simplemente delega el trabajo real en el auxiliar interno __list_add, implementado así:

static __always_inline void __list_add(struct list_head *new,
                       struct list_head *prev,
                       struct list_head *next)
{
    if (!__list_add_valid(new, prev, next))
        return;

    next->prev = new;
    new->next = next;
    new->prev = prev;
    WRITE_ONCE(prev->next, new);
}

El resto de las operaciones básicas sigue la misma idea. Hay auxiliares para eliminar nodos, agregarlos al final de una lista, moverlos entre listas y recorrer los elementos.

No los revisaré uno por uno. Con los conceptos que ya conocemos, leer su implementación en include/linux/list.h puede ser un buen ejercicio.

Conclusión

El kernel Linux no guarda los objetos dentro de los nodos de sus listas, sino los nodos dentro de los objetos: un struct list_head con dos punteros, incrustado en la estructura que se quiere enlazar. container_of (y su alias list_entry) recupera la estructura contenedora restando el desplazamiento del miembro, y operaciones como list_add solo reajustan cuatro punteros. Esa combinación mantiene la implementación genérica y evita una reserva de memoria por cada nodo, y es la base de buena parte de las estructuras que aparecen en los subsistemas del kernel.

Zig frente a C: notas para programación de sistemas

C sigue siendo el lenguaje que más leo. Para código nuevo prefiero Zig: mantiene el mismo nivel de control y detecta más errores en compilación o en modo debug. Estas son las diferencias que más pesan en la práctica.

1. Liberar recursos: goto vs defer/errdefer

En C, la limpieza en orden inverso suele resolverse con una cadena de etiquetas:

int load(const char *path, char **out) {
    int rc = -1;
    FILE *f = fopen(path, "rb");
    if (!f) goto done;

    char *buf = malloc(4096);
    if (!buf) goto close_file;

    if (fread(buf, 1, 4096, f) == 0) goto free_buf;

    *out = buf;
    rc = 0;
    goto close_file;

free_buf:
    free(buf);
close_file:
    fclose(f);
done:
    return rc;
}

En Zig, cada recurso declara su limpieza junto a su adquisición:

fn load(gpa: std.mem.Allocator, path: []const u8) ![]u8 {
    const file = try std.fs.cwd().openFile(path, .{});
    defer file.close(); // siempre

    const buf = try gpa.alloc(u8, 4096);
    errdefer gpa.free(buf); // solo si se retorna un error

    const n = try file.read(buf);
    if (n == 0) return error.EmptyFile;
    return try gpa.realloc(buf, n);
}

defer se ejecuta al salir del bloque y errdefer, solo en la salida por error. Agregar un recurso nuevo no obliga a reordenar etiquetas.

Las rutas de fallo también se pueden probar. checkAllAllocationFailures repite la función y hace fallar cada asignación, una por una. std.testing.allocator reporta las fugas de memoria:

test "load no pierde memoria" {
    try std.testing.checkAllAllocationFailures(std.testing.allocator, loadForTest, .{});
}

2. La longitud viaja con el dato

int sum(const int *xs, size_t n) {
    int s = 0;
    for (size_t i = 0; i <= n; i++)   /* lee xs[n]: fuera de rango */
        s += xs[i];
    return s;
}

C compila esto sin advertencias y lee memoria ajena en silencio. En Zig, un slice ([]T) es puntero + longitud:

fn sum(xs: []const i32) i32 {
    var s: i32 = 0;
    for (xs) |x| s += x;
    return s;
}

Con el mismo error de índice, el resultado es un panic inmediato en Debug y ReleaseSafe:

var i: usize = 0;
while (i <= xs.len) : (i += 1) s += xs[i];
// panic: index out of bounds: index 3, len 3

Los strings son []const u8: no hace falta strlen() ni existe el terminador \0 olvidado.

3. Errores que no se pueden ignorar

FILE *f = fopen("config.ini", "r");
fgets(line, sizeof line, f);   /* si f es NULL: comportamiento indefinido */

En Zig, el error forma parte del tipo de retorno (!T). El compilador obliga a manejarlo:

const file = std.fs.cwd().openFile("config.ini", .{}) catch |err| switch (err) {
    error.FileNotFound => return defaultConfig(),
    else => return err,
};
defer file.close();

Si se omite el resultado, el programa no compila:

std.fs.cwd().deleteFile("tmp.txt");
// error: error union is ignored

Las opciones son try (propagar), catch (manejar) o if (x) |v| ... else |err| ....

4. comptime en lugar del preprocesador

Las macros de C sustituyen texto:

#define MAX(a, b) ((a) > (b) ? (a) : (b))
int m = MAX(i++, j);   /* i++ puede evaluarse dos veces */

#ifdef _WIN32
#define SEP '\\'
#else
#define SEP '/'
#endif

En Zig se escribe código normal que se evalúa en compilación:

const builtin = @import("builtin");

fn max(comptime T: type, a: T, b: T) T {
    return if (a > b) a else b;
}

const sep: u8 = if (builtin.os.tag == .windows) '\\' else '/';

Para los genéricos se usa una función que retorna un tipo:

fn Stack(comptime T: type, comptime cap: usize) type {
    return struct {
        items: [cap]T = undefined,
        len: usize = 0,

        pub fn push(self: *@This(), x: T) error{Full}!void {
            if (self.len == cap) return error.Full;
            self.items[self.len] = x;
            self.len += 1;
        }
    };
}

var s: Stack(u32, 16) = .{};
try s.push(42);

Los argumentos se evalúan una sola vez, hay comprobación de tipos y los errores de compilación son legibles.

5. Overflow con semántica explícita

int x = INT_MAX;
x = x + 1;   /* overflow con signo: comportamiento indefinido */

En Zig, la intención se escribe en el operador:

const x: i32 = std.math.maxInt(i32);

const w = x +% 1;                 // wrapping:   -2147483648
const s = x +| 1;                 // saturación:  2147483647
const r = @addWithOverflow(x, 1); // .{ -2147483648, 1 }

var y = x;
y += 1; // Debug/ReleaseSafe: panic: integer overflow

6. Zig también compila C

zig cc es un compilador de C (Clang) con soporte de compilación cruzada integrado:

zig cc -O2 -o hello hello.c
zig cc -target x86_64-linux-musl -static -o hello hello.c
zig cc -target aarch64-macos -o hello hello.c

C y Zig pueden convivir en el mismo build.zig:

exe.root_module.addCSourceFile(.{
    .file = b.path("src/legacy.c"),
    .flags = &.{"-std=c11"},
});
exe.root_module.link_libc = true;

Esto permite migrar un proyecto archivo por archivo.

7. Límites

  • Zig no evita use-after-free ni punteros a variables locales que ya no existen.
  • En ReleaseFast y ReleaseSmall se eliminan casi todas las comprobaciones de seguridad.
  • El lenguaje aún no llega a 1.0, así que sus APIs cambian entre versiones.
  • C tiene un ABI estable, más ecosistema y soporte para más arquitecturas.

Para leer código existente, C sigue siendo indispensable. Para escribir código nuevo, Zig ofrece el mismo control y más errores detectados antes de producción.

memcpy(nullptr, nullptr, 0) y otros casos de comportamiento indefinido en C

El comportamiento indefinido (UB) en el lenguaje de programación C es una fuente regular de acaloradas discusiones entre programadores. Por un lado, el UB puede ser importante para las optimizaciones del compilador. Por otro lado, facilita la introducción de errores que pueden llevar a problemas de seguridad.

La buena noticia es que N3322 ha sido aceptado para C2y, lo cual eliminará el comportamiento indefinido de un rincón específico del lenguaje C, haciendo que lo siguiente sea bien definido:

memcpy(nullptr, nullptr, 0);
memcmp(nullptr, nullptr, 0);
(int *)nullptr + 0;
(int *)nullptr - 0;
(int *)nullptr - (int *)nullptr;

Esto solo se aplica cuando un puntero nulo se combina con una operación de "longitud cero". Lo siguiente sigue siendo indefinido:

memcpy(nullptr, nullptr, 4);
(int *)nullptr + 4;

La eliminación de este comportamiento indefinido no se espera que tenga un impacto negativo en el rendimiento. De hecho, ocurre lo contrario.

Motivación

Los ejemplos anteriores son un poco tontos porque codifican de manera dura una constante NULL/nullptr. Sin embargo, es fácil encontrarse con esta situación con un puntero que a veces es nulo. Por ejemplo, considere una representación típica para una cadena con una longitud conocida:

struct str {
   char *data;
   size_t len;
};

Una cadena vacía normalmente se representaría como (struct str) { .data = nullptr, .len = 0 }, con el puntero de datos siendo nullptr. Ahora, considere una función que comprueba si dos cadenas son iguales:

bool str_eq(const struct str *str1, const struct str *str2) {
   return str1->len == str2->len &&
          memcmp(str1->data, str2->data, str1->len) == 0;
}

Esta implementación parece razonable a primera vista. Sin embargo, muestra comportamiento indefinido si ambas entradas son cadenas vacías. En ese caso, llamaremos a memcmp(nullptr, nullptr, 0), lo cual es comportamiento indefinido según el estándar de C.

Este tipo de UB introduce el riesgo de que el compilador optimice las comprobaciones de punteros nulos subsiguientes. Por ejemplo, GCC eliminará alegremente la rama dest == nullptr en el siguiente código, mientras que Clang deliberadamente no realiza esta optimización:

int test(char *dest, const char *src, size_t len) {
   memcpy(dest, src, len);
   if (dest == nullptr) {
       // Esta rama será eliminada por GCC debido al comportamiento indefinido.
   }
}

La manera correcta de escribir la función str_eq es:

bool str_eq(const struct str *str1, const struct str *str2) {
   return str1->len == str2->len &&
          (str1->len == 0 ||
           memcmp(str1->data, str2->data, str1->len) == 0);
}

El nuevo código es correcto, pero peor en todos los demás aspectos:

  • Aumenta el tamaño del código, requiriendo una comprobación adicional en cada sitio de llamada inlinada.
  • Disminuye el rendimiento, comprobando redundante algo que memcmp debe manejar de todas formas.
  • Aumenta la complejidad del código.

Al mismo tiempo, no hay una manera útil en la que la biblioteca de C pueda aprovechar este comportamiento indefinido para proporcionar una implementación más eficiente. Este es el tipo de UB que no beneficia a nadie y debería ser eliminado del lenguaje.

Aritmética de puntero nulo

La propuesta original se centró en eliminar UB para las llamadas de la biblioteca de memoria, pero un revisor temprano señaló que esto no es suficiente. Después de todo, también necesitamos tener en cuenta cómo se implementan estas funciones de biblioteca.

Por ejemplo, consideremos una implementación típica para una función tipo memcpy:

void copy(char *dst, const char *src, size_t n) {
   for (const char *end = src + n; src < end; src++) {
       *dst++ = *src;
   }
}

Esta función muestra comportamiento indefinido cuando se llama como copy(nullptr, nullptr, 0), porque nullptr + 0 es comportamiento indefinido en C.

Para evitar esto, y hacer que el lenguaje sea autoconsistente, necesitamos definir nullptr + 0 como devolviendo nullptr y nullptr - nullptr como devolviendo 0. Esto también alinea C con las semánticas de C++, donde esto ya estaba bien definido.

Oposición

Cuando se discutió esta propuesta en dos reuniones de WG14, la oposición no vino de la dirección que esperaba.

La parte más controvertida de la propuesta fue definir nullptr - nullptr como devolviendo 0. La razón para esto es que cuando los espacios de direcciones entran en juego (que no son parte del C estándar, pero pueden ser implementados como extensión), puede haber múltiples representaciones de un puntero nulo. Asegurarse de que la resta de dos "diferentes" nulos aún resulte en cero podría requerir la generación de código adicional, rompiendo la premisa de que este cambio es completamente gratuito.

Sin embargo, la oposición más vocal vino desde la perspectiva del análisis estático: Haciendo que los punteros nulos sean bien definidos para longitud cero significa que los analizadores estáticos ya no pueden reportar incondicionalmente nullptr siendo pasado a funciones como memcpy—también deben tener en cuenta la longitud ahora. Si un calificador _Optional se introduce en el futuro, los argumentos de memcpy tendrían que ser calificados con él. GCC está considerando la introducción de un atributo nonnull_if_nonzero para representar la nueva precondición.

Después de la discusión aparentemente negativa, me sorprendió que el voto no solo fuera fuertemente a favor del cambio, sino que también viniera con una recomendación a los implementadores para aplicar el cambio retroactivamente a versiones antiguas del estándar. Esto significa que, una vez que los compiladores y las bibliotecas de C hayan implementado el cambio, debería aplicarse incluso sin especificar la bandera -std=c2y.

Funciones integradas del compilador

Trabajo en el medio de la cadena de herramientas de compilador LLVM. Al estar lejos de cualquier parte "orientada al usuario" del compilador, generalmente no estoy involucrado en esfuerzos de estandarización.

La razón por la que me involucré aquí fue la especificación para el intrínseco interno de memcpy de LLVM:

Los intrínsecos llvm.memcpy.* copian un bloque de memoria desde la ubicación de origen a la ubicación de destino, que deben ser iguales o no superpuestas. [...]

Si es 0, es un no-op modulo el comportamiento de los atributos adjuntos a los argumentos. [...]

El intrínseco llvm.memcpy puede reducirse a una llamada a la función memcpy, que se trata aquí como un "compilador runtime builtin", aunque en última instancia también es proporcionada por la biblioteca C.

Cuando se usa como un builtin, LLVM requiere que tanto memcpy(x, x, s) como memcpy(nullptr, nullptr, 0) estén bien definidos, aunque el estándar C dice que son UB. GCC y MSVC tienen suposiciones similares.

Hacer que memcpy(nullptr, nullptr, 0) sea oficialmente bien definido elimina una de las suposiciones, mientras que el caso de memcpy(x, x, s) permanece por ahora. Permitir esto fue originalmente también parte de la propuesta, pero más tarde se descartó porque no encajaba bien con los otros cambios.

En un giro extraño de los eventos, este cambio en el estándar de C surgió porque los desarrolladores de Rust seguían quejándose sobre la discrepancia entre las semánticas de LLVM y C.

Algunas características de C++

Características de C++26

Bucles infinitos triviales y UB

Esta propuesta acerca un poco más a C y C++. El estándar de C++ definía el progreso hacia adelante de manera que asumía que incluso los bucles infinitos triviales terminarían; si no lo hacían, el programa entraba en comportamiento indefinido (UB). Esto es un problema si escribes código de bajo nivel donde estos bucles son comunes. La propuesta añade una definición de una declaración de iteración trivialmente vacía, donde un bucle cuya expresión de control es una expresión constante que evalúa a true es un bucle infinito trivial; ahora estos se incluyen en la definición de progreso hacia adelante. Por ejemplo, en GCC 14, el siguiente fragmento ya no causa comportamiento indefinido (en todos los dialectos de C++, no solo C++26):

void
g ()
{
  while (true)
  /* do something */
}

Almacenamiento estático para inicializadores con llaves

Esta propuesta, implementada en GCC 14, permite al compilador optimizar mejor el código que usa std::initializer_list. La implementación de std::initializer_list usa un array de respaldo para sus datos. Antes de esta propuesta, el estándar no permitía al compilador asignar el array de respaldo en almacenamiento estático incluso cuando los datos eran constantes porque todos los arrays de respaldo tenían que ser distintos. Ahora, esta restricción ya no está mandatada, permitiendo que los arrays de respaldo se compartan (lo cual ya era el caso para las cadenas literales). En resumen, GCC 14 optimiza eliminando las llamadas memcpy que copian el array de respaldo en el siguiente fragmento:

#include <initializer_list>
void f(std::initializer_list<int> il);
void g() {
   f({3,2,1, 0, 1, 2, 3}); // array en .rodata
}

Cadenas no evaluadas

GCC 14, en modo C++26, implementa P2361R6, que introduce el concepto de cadenas no evaluadas. Estas cadenas aparecen en contextos como _Pragma, static_assert, o los atributos [[nodiscard]] y [[deprecated]]. No se usan en tiempo de ejecución, por lo que no se convierten a la codificación de ejecución como las cadenas evaluadas. Dado que no se convertirán a otro tipo de codificación de cadena, no pueden contener secuencias de escape numéricas ni prefijos. En la práctica, esto significa que las siguientes dos líneas causarán diagnósticos en modo C++26:

static_assert (true, u"foo"); // error en C++26
static_assert (true, "\x{20}"); // advertencia en C++26 en modo pedántico

constexpr cast desde void*

GCC 14 implementa P2738R1, lo que significa que el siguiente test es aceptado en C++26. Esta característica permite realizar varios trucos de borrado de tipo en código constexpr. (En C++23 y antes, el compilador todavía emitía un error al intentar hacer un cast desde void* en una expresión constante):

struct A { int i; };
struct B { A a; };
constexpr int f()
{
  B b { 42 };
  void *p = &b;
  A* ap = static_cast<A*>(p); // OK
  return ap->i;
}
static_assert (f() == 42);

Mensajes de static_assert generados por el usuario

Con esta propuesta implementada en GCC 14, los usuarios pueden usar static_assert de manera más general ya que ahora acepta mensajes generados por el usuario (que deben ser evaluados como constantes). Por ejemplo:

struct error {
  constexpr int size () const { return sizeof "hello" - 1; }
  constexpr const char *data () const { return "hello"; }
};
static_assert (false, error{});

Esto produce el siguiente mensaje de error:

error: static assertion failed: hello

Variables placeholder

GCC 14 implementa la propuesta P2169R4. Esta propuesta permite usar la variable especial _, que actúa como marcador de posición para una variable sin nombre que no produce el diagnóstico de "variable no usada" incluso cuando no se usa. _ también puede redefinir una declaración existente en el ámbito actual (pero usar _ generaría un error si más de una variable se ha declarado con ese nombre):

X foo ();
void
g ()
{
  auto _ = foo ();
  auto _ = 42;       // OK
  int i = _;         // error: referencia a ‘_’ es ambigua
}

Retorno de referencia a temporal

P2748R5 hace que sea mal formado retornar una referencia a un temporal. GCC ha advertido sobre este tipo de código peligroso por mucho tiempo, pero C++26 lo convierte en un error:

auto&&
foo ()
{
  return 42;  // mal formado en C++26
}

Características de C++23

Deducir this

GCC 14 implementó esta propuesta, muy solicitada. Permite añadir un parámetro this explícito a las funciones miembro no estáticas; esto se denomina parámetro de objeto explícito. De esta manera, puedes deducir el tipo y la categoría de valor del objeto de la clase. Es útil para evitar la duplicación de código; antes, el desarrollador tenía que escribir varias sobrecargas de funciones miembro: no-const, const, y con calificadores de referencia incluso const & y && (ignorando detalles como volatile). Con esta propuesta, en lugar de:

class S {
  int value;
public:
  int get_add (int i) & { return value + i; }
  int get_add (int i) && { return value + i; }
  int get_add (int i) const & { return value + i; }
};
auto g (S s, const S& sr) -> int
{
  auto i1 = s.get_add (42);
  auto i2 = sr.get_add (42);
  auto i3 = S{}.get_add (42);
  return i1 + i2 + i3;
}

Puedes simplificar el código a:

class S {
  int value;
public:
  template<typename Self>
  int get_add (this Self&& self, int i) { return self.value + i; }
};
S s{};
s.get_add(1);                // Self se deduce como S&
std::move(s).get_add(2);     // Self se deduce como S
std::as_const(s).get_add(3); // Self se deduce como const S&

Deducir this también permite escribir lambdas recursivas. Por ejemplo:

int
main ()
{
  auto fib = [](this auto self, int n) {
    if (n < 2)
      return n;
    return self (n - 1) + self (n - 2);
  };
  static_assert (fib (6) == 8);
}

Hay muchos más ejemplos donde el parámetro de objeto explícito puede ser útil. Tiene algunas restricciones; por ejemplo, una función miembro explícita no puede ser estática o virtual.

Referencias en expresiones constantes

Una forma moderna de C++ para implementar una función que obtenga el tamaño de un array puede ser:

template<typename T, size_t N>
constexpr auto array_size (T (&)[N]) -> size_t {
  return N;
}

Esta función se puede usar como en el siguiente ejemplo:

void g ()
{
  int arr[] = { 1, 3, 3, 7 };
  constexpr auto sz = array_size (arr);
}

El código funciona sin sorpresas. Sin embargo, cuando el array era un parámetro, como en este ejemplo:

void g (const int (&arr)[3])
{
  constexpr auto sz = array_size (arr);
}

El compilador, debido a ciertas reglas bastante complejas, rechazaba el código con el error: ‘arr’ no es una expresión constante. Las reglas se han ajustado y el código funciona como se espera con GCC 14 (en todos los dialectos de C++).

consteval necesita propagarse hacia arriba

Implementar esta propuesta en GCC 14 resultó algo complicado. Hace que ciertas funciones se promuevan a consteval, es decir, convertir en funciones inmediatas. Considera:

consteval int id(int i) { return i; }
template <typename T>
constexpr int f(T t)
{
  return t + id(t); // id causa que f<int> se promueva a consteval
}
void g(int i)
{
  f (3);
}

Anteriormente, el código era inválido y el compilador emitía un error diciendo que t en f no era una expresión constante válida. Con esta propuesta, f se promueve a consteval, lo que significa que la llamada id(t) está en un contexto inmediato, por lo que la llamada no necesita ser una expresión constante. (Así es como funciona la composición de funciones consteval – una función consteval llamando a otra). Ten en cuenta que hacer f consteval implica que la llamada f(3) debe ser una expresión constante válida.

El estándar describe cuáles expresiones causan que su función envolvente se promueva a consteval; estas expresiones se llaman inmediatas-escaladas. Por ejemplo, una llamada a una función inmediata (es decir, consteval) que no es una expresión constante y no es una subexpresión de una invocación inmediata es una expresión inmediata-escalada. No todas las funciones pueden promoverse a consteval. El estándar dice que solo las funciones de escalada inmediata pueden promoverse. Un ejemplo de función de escalada inmediata es una función de plantilla declarada como constexpr.

El comportamiento descrito en la propuesta está habilitado por defecto en el modo C++20 o posterior, pero puedes suprimir la escalada de funciones con la opción de línea de comandos -fno-immediate-escalation.

CTAD desde constructores heredados

GCC 14 soporta P2582R1, una propuesta que extiende CTAD (Deducción de Argumentos de Plantilla de Clase) para constructores heredados. Por lo tanto, el siguiente caso de prueba compila en modo C++23:

template <typename T> struct B {
B(T);
};
template <typename T> struct C : B<T*> {
using B<T*>::B;
};

int* p;
C c(p); // OK, deduce C<int>

Resolución de informes de defectos

GCC 14 implementa varias resoluciones de informes de defectos, que generalmente se aplican a todos los dialectos afectados por -std, no solo a los estándares más nuevos. Consulta nuestra tabla de DR de C++ para un estado más detallado.

stricter constinit

El problema CWG 2543 aclara que las variables constinit con inicializadores no constantes deben ser diagnosticadas, incluso si la variable podría inicializarse estáticamente.

goto y objetos inicializados trivialmente

Desde el problema CWG 2256, goto puede cruzar la inicialización de un objeto inicializado trivialmente con un destructor no trivial:

struct A {
  ~A() { }
};
void f()
{
  goto L;
  A a;
L:
  return;
}
