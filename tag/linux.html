Lista doblemente enlazada en el kernel Linux

El kernel Linux es una pieza de código enorme. Como todo kernel de un sistema operativo moderno, contiene planificadores que administran procesos y recursos, una pila de red, varios sistemas de archivos, miles de controladores de dispositivos y muchísimo más. Al mismo tiempo, tiene que gestionar todo esto de la forma más eficiente posible. Y la eficiencia no siempre consiste en escribir instrucciones más rápidas o algoritmos ingeniosos. Muy a menudo, como en cualquier aplicación de espacio de usuario, empieza con una pregunta mucho más fundamental: ¿cómo están organizados los datos?

Como escribió alguna vez Linus Torvalds:

Los buenos programadores se preocupan por las estructuras de datos y sus relaciones.

— Linus Torvalds, lista de correo de git, 27 de julio de 2006

El kernel necesita llevar la cuenta de procesos, páginas de memoria, archivos, temporizadores, dispositivos, conexiones de red e innumerables objetos más. Algunos deben buscarse rápido, otros deben mantenerse siempre ordenados, otros se recorren con frecuencia y otros tienen que insertarse o eliminarse con el menor costo posible. Elegir una representación adecuada para estos datos puede influir directamente en el rendimiento y en el consumo de memoria.

Esto es especialmente importante en un software como el kernel de un sistema operativo. Idealmente, debería ser casi invisible para el usuario y añadir la menor sobrecarga posible.

Si alguna vez has leído el código fuente del kernel, probablemente notaste que listas enlazadas, árboles, colas, mapas de bits, tablas hash y muchas otras estructuras de datos aparecen en casi todos sus subsistemas. Algunas resultan familiares por los libros clásicos de ciencias de la computación; otras se adaptaron a los requisitos particulares y al estilo de programación del kernel.

En este artículo veremos uno de estos bloques básicos, para reconocerlo cuando exploremos los principales subsistemas del kernel.

Listas enlazadas

La primera estructura de datos que veremos es la lista enlazada.

Me parece una buena elección para empezar porque, por un lado, es relativamente sencilla y, por otro, es omnipresente. Decir que es omnipresente no es exagerar: encontramos listas enlazadas en muchas partes distintas del kernel. Para tener una idea aproximada de cuán común es:

rg -w 'struct list_head' | wc -l
17143

¡Más de diecisiete mil apariciones! Sin duda vale la pena entender cómo se implementa y se usa la lista enlazada en el kernel.

Uno de los usos principales de esta estructura es organizar distintos tipos de objetos en secuencias. Pero antes de entrar en la implementación del kernel, repasemos brevemente la estructura en general.

Según Wikipedia:

En ciencias de la computación, una lista enlazada es una estructura de datos lineal compuesta por una secuencia de nodos. Cada nodo almacena uno o más valores de datos y una o varias referencias —también llamadas enlaces o punteros— hacia otros nodos de la lista.

— Wikipedia, «Lista enlazada»

En otras palabras, a diferencia de un arreglo, los elementos de una lista enlazada no tienen que ocupar posiciones contiguas en memoria. La relación entre ellos se representa explícitamente mediante enlaces. En el caso más simple, cada nodo contiene un único enlace al nodo siguiente:

Una lista así se llama lista simplemente enlazada y solo puede recorrerse en un sentido: partimos de head y seguimos el puntero next de cada nodo hasta llegar al final. Su definición y la implementación de sus operaciones básicas son bastante simples. Si has leído, por ejemplo, Algorithms de Robert Sedgewick y Kevin Wayne, conoces la representación clásica:

private class Node
{
    Item item;
    Node next;
}

Cada Node guarda un elemento y una referencia al nodo siguiente. Por ejemplo, si la lista contiene tres elementos, el primer nodo apunta al segundo y el segundo al tercero. El último nodo no apunta a nada: su enlace vale null, y así se determina el final de la lista.

Agregar un elemento nuevo no exige mover los elementos existentes en memoria: basta con crear un nodo y ajustar los enlaces correspondientes. Para eliminar un elemento, cambiamos el enlace del nodo anterior para que se salte el nodo eliminado.

Muchas veces esto no es suficiente. Algunas operaciones necesitan recorrer la lista hacia atrás. En esos casos, cada nodo recibe un segundo enlace que apunta al nodo anterior. Esta estructura se llama lista doblemente enlazada y, esquemáticamente, se ve así:

Listas enlazadas en el kernel Linux

Una vez repasada la idea básica, veamos cómo las implementa el kernel Linux.

Antes de ver esa implementación, esperaba algo muy parecido a lo anterior: una estructura simple con un puntero o espacio para los datos y una referencia a otro nodo. ¡Resultó ser bastante distinta!

El kernel implementa las llamadas listas enlazadas intrusivas. En ellas no hay un puntero a los datos. El nodo de la lista contiene solo dos punteros: uno al elemento siguiente y otro al anterior. Ese nodo se incrusta dentro de la estructura que queremos guardar en la lista, y los enlaces conectan estos nodos incrustados:

Sí, al principio puede parecer muy raro. ¿Cómo puede una estructura así representar una lista de procesos, dispositivos, archivos o cualquier otro objeto del kernel si no contiene los objetos? La respuesta es justamente una de las ideas características de la implementación de Linux: en lugar de guardar el objeto dentro del nodo de la lista, se guarda el nodo de la lista dentro del objeto.

La implementación de las listas enlazadas del kernel está en include/linux/list.h. La estructura en sí refleja la idea que acabamos de describir:

struct list_head {
    struct list_head *next, *prev;
};

La estructura list_head contiene solo dos punteros: al nodo siguiente y al anterior. ¿Cómo se usa, entonces? Se incrusta un list_head directamente en la estructura cuyos objetos queremos mantener en una lista. Por ejemplo, la estructura que define un proceso tiene, entre otros campos:

struct task_struct {
    ...
    struct list_head tasks;
    ...
};

El campo tasks sirve para enlazar objetos task_struct entre sí. Así, en lugar de reservar un nodo de lista aparte que contenga un puntero a un task_struct, cada task_struct contiene su propio nodo. Lo interesante es que los punteros next y prev no apuntan directamente a otro task_struct, sino al miembro tasks incrustado en los task_struct vecinos. Esquemáticamente:

Este enfoque nos da una lista enlazada sin reservar memoria aparte para cada nodo y sin que list_head tenga que saber nada de las estructuras que enlaza.

Suena muy bien, pero la primera vez que uno lo ve surge otra pregunta: si al recorrer la lista solo tenemos un puntero a list_head, ¿cómo volvemos al task_struct que lo contiene? La respuesta se apoya en otro auxiliar muy común del kernel: la macro container_of. Esta macro nos da un puntero a la estructura que nos interesa; en nuestro caso, a partir de un puntero al miembro tasks obtenemos el task_struct que lo contiene.

La idea es bastante simple. Si conocemos la dirección de un nodo de lista incrustado en una estructura, el tipo de la estructura y el nombre del campo que representa el nodo, podemos calcular la dirección de la propia estructura. Aquí tenemos un puntero al miembro tasks, que es un list_head, y sabemos que ese miembro pertenece a la estructura task_struct. Con esa información, el kernel obtiene la dirección del task_struct.

Esto es exactamente lo que permite que la implementación de las listas siga siendo genérica: list_head no sabe nada de task_struct, y aun así el código que usa la lista siempre puede volver al objeto que contiene el nodo.

Entendida la idea básica, veamos la implementación de container_of. La definición de la macro está en include/linux/container_of.h:

/**
 * container_of - cast a member of a structure out to the containing structure
 * @ptr:    the pointer to the member.
 * @type:   the type of the container struct this is embedded in.
 * @member: the name of the member within the struct.
 *
 * WARNING: any const qualifier of @ptr is lost.
 * Do not use container_of() in new code.
 */
#define container_of(ptr, type, member) ({              \
    static_assert(__same_type(*(ptr), typeof_member(type, member)) || \
              __same_type(*(ptr), void),            \
              "pointer type mismatch in container_of()");   \
    (type *)((void *)(ptr) - offsetof(type, member)); })

La macro recibe tres argumentos:

  • el puntero al nodo de la lista;
  • el tipo de la estructura que contiene el nodo;
  • el nombre del campo que representa el nodo.

En el ejemplo anterior, estos argumentos corresponderían a:

  • el puntero al campo tasks;
  • struct task_struct, como tipo que contiene el nodo;
  • tasks, como nombre del campo que representa el nodo.

La primera línea del cuerpo de la macro no tiene que ver con el cálculo de la dirección: solo hace una comprobación de tipos en tiempo de compilación para asegurar que el puntero al nodo tenga el tipo esperado.

La segunda línea hace el trabajo real. Con la macro offsetof calcula el desplazamiento desde el inicio de la estructura hasta el campo que define el nodo. Conocido ese desplazamiento, lo restamos de la dirección del nodo y obtenemos la dirección de la estructura que lo contiene.

¡Y eso es básicamente todo! En abstracto, container_of nos da la dirección de una estructura cuando conocemos la dirección de uno de sus campos. Llevado al contexto de las listas enlazadas, no es más que obtener la entrada real de la lista a partir de un puntero a su nodo incrustado:

/**
 * list_entry - get the struct for this entry
 * @ptr:    the &struct list_head pointer.
 * @type:   the type of the struct this is embedded in.
 * @member: the name of the list_head within the struct.
 */
#define list_entry(ptr, type, member) \
    container_of(ptr, type, member)

Operaciones sobre listas

En la sección anterior conocimos la estructura básica de las listas enlazadas del kernel. Ahora veamos las operaciones para agregar, eliminar y actualizar elementos.

Simplemente enumerar la API existente sería bastante aburrido. Es mucho más interesante ver un ejemplo real de uso: algún mecanismo que probablemente hayas visto al usar Linux, pero sin pensar en lo que ocurre por detrás.

El kernel usa listas en muchísimos lugares. Tomemos, por ejemplo, los dispositivos de caracteres misceláneos (misc).

Cada dispositivo de caracteres se identifica con un par de números: el número mayor (major) y el menor (minor). El mayor suele identificar al controlador o a un grupo de dispositivos relacionados, y el menor, a un dispositivo concreto que maneja ese controlador.

El kernel ofrece una API especial que permite a un controlador registrar un dispositivo de caracteres sin asignarle un número mayor propio. Todos esos dispositivos comparten el mismo número mayor y cada uno recibe su propio número menor. Ese número mayor es:

#define MISC_MAJOR      10

Podemos ver los dispositivos misceláneos registrados con el siguiente comando:

Desde el espacio de usuario, los dispositivos misceláneos se ven como dispositivos de caracteres normales con el mismo número mayor y distintos números menores. Lo que nos interesa es cómo el kernel lleva internamente la cuenta de todos ellos.

Cada dispositivo misceláneo se representa con una estructura miscdevice, definida en include/linux/miscdevice.h. Entre otros, esta estructura tiene un campo llamado list, que permite al dispositivo formar parte de la lista enlazada que mantiene el subsistema misc:

struct miscdevice {
    int minor;
    const char *name;
    const struct file_operations *fops;
    struct list_head list;
    struct device *parent;
    struct device *this_device;
    const struct attribute_group **groups;
    const char *nodename;
    umode_t mode;
};

Ya sabemos cómo usará el kernel el campo list: cada dispositivo registrado contiene su propio nodo, y todos están enlazados en una única lista con la que el kernel les sigue la pista. Hasta aquí debería quedar claro cómo se manejan y enlazan los nodos. Pero ¿cómo accedemos a la lista en sí? Necesitamos una referencia a su cabeza:

static LIST_HEAD(misc_list);

Siguiendo las definiciones de las macros LIST_HEAD y LIST_HEAD_INIT en include/linux/list.h, esto se expande a una inicialización de estructura C corriente:

struct list_head misc_list = { &(misc_list), &(misc_list) }

Los dos valores del inicializador son los campos next y prev de la estructura list_head. Como al principio la lista está vacía, no hay otros nodos a los que apuntar, así que ambos apuntan a la propia cabeza.

Cuando el kernel registra un dispositivo, inicializa la estructura miscdevice correspondiente y la agrega a la lista con:

list_add(&misc->list, &misc_list);

Esta función está definida en include/linux/list.h y luce así:

static __always_inline void list_add(struct list_head *new,
                     struct list_head *head)
{
    __list_add(new, head, head->next);
}

Simplemente delega el trabajo real en el auxiliar interno __list_add, implementado así:

static __always_inline void __list_add(struct list_head *new,
                       struct list_head *prev,
                       struct list_head *next)
{
    if (!__list_add_valid(new, prev, next))
        return;

    next->prev = new;
    new->next = next;
    new->prev = prev;
    WRITE_ONCE(prev->next, new);
}

No los revisaré uno por uno. Con los conceptos que ya conocemos, leer su implementación en include/linux/list.h puede ser un buen ejercicio.

Conclusión

El kernel Linux no guarda los objetos dentro de los nodos de sus listas, sino los nodos dentro de los objetos: un struct list_head con dos punteros, incrustado en la estructura que se quiere enlazar. container_of (y su alias list_entry) recupera la estructura contenedora restando el desplazamiento del miembro, y operaciones como list_add solo reajustan cuatro punteros. Esa combinación mantiene la implementación genérica y evita una reserva de memoria por cada nodo, y es la base de buena parte de las estructuras que aparecen en los subsistemas del kernel.
